# Apex Sourcing

منصة رقمية لإدارة طلبات الاستيراد بالوكالة — راجع `docs/` للتصميم الكامل قبل قراءة أي كود:

- [`docs/state-machine.md`](docs/state-machine.md) — جدول الانتقالات الرسمي (مصدر الحقيقة الوحيد لآلة الحالة).
- [`docs/data-model.md`](docs/data-model.md) — نموذج البيانات الكامل ومصفوفة الصلاحيات.
- [`docs/schema.sql`](docs/schema.sql) — DDL مرجعي لـ PostgreSQL (الهجرات الفعلية في `migrations/` مشتقة منه حرفياً).

بنية المستودع: `packages/domain` (منطق آلة الحالة، بلا قاعدة بيانات) + `apps/api` (NestJS، الخادم الفعلي).

## المتطلبات

- Node.js ≥ 20، pnpm
- PostgreSQL 16 (محلياً أو عبر `docker-compose up -d`)

## الإعداد

```bash
pnpm install

# انسخ .env وعدّل القيم حسب بيئتك (الأسرار افتراضية للتطوير المحلي فقط)
cp .env.example .env   # إن لم يوجد .env بعد

# ينشئ الأدوار اللازمة على مستوى Postgres قبل أول هجرة:
#   - دور تشغيل الهجرات (سوبر يوزر أو صلاحيات كافية) — يُستخدم في DATABASE_URL
#   - app_role: الدور الذي يتصل به الخادم فعلياً (RLS و REVOKE على audit_log يُفرَضان عليه تحديداً)
psql -c "CREATE ROLE apex_migrator WITH LOGIN PASSWORD '...' SUPERUSER;"
psql -c "CREATE DATABASE apex_dev OWNER apex_migrator;"

pnpm --filter @apex/api migrate
psql -d apex_dev -c "ALTER ROLE app_role WITH PASSWORD '...';"   # يطابق APP_DATABASE_URL في .env
```

## التشغيل

```bash
pnpm --filter @apex/api dev      # تطوير مع إعادة تحميل تلقائي
pnpm --filter @apex/api build && pnpm --filter @apex/api start:prod
```

الخادم يُقلِع على `PORT` (افتراضياً 3000). توثيق OpenAPI التفاعلي على `/docs`.

**مهم**: الخادم يتصل دوماً كـ`app_role`، أبداً كدور الهجرات — RLS و`REVOKE UPDATE/DELETE` على `audit_log` مفروضان تحديداً على هذا الدور، والاتصال بدور مختلف (كالمالك) يتجاوزهما بصمت.

## متغيرات البيئة (`.env`)

| المتغير | الوصف |
|---|---|
| `DATABASE_URL` | اتصال بصلاحيات كافية لتشغيل الهجرات فقط (سكربتات `migrate`/`migrate:down`) — لا يستخدمه الخادم وقت التشغيل |
| `APP_DATABASE_URL` | اتصال `app_role` — هذا ما يستخدمه الخادم فعلياً |
| `JWT_CUSTOMER_SECRET` / `JWT_SUPPLIER_SECRET` / `JWT_ADMIN_SECRET` | أسرار توقيع JWT منفصلة لكل جمهور (3 جلسات مستقلة تماماً) |
| `BIDDING_DEADLINE_MS` | مدة نافذة المزايدة المغلقة بالميلي ثانية — افتراضياً 72 ساعة (`259200000`)؛ تُقصَّر بيئياً للاختبار/التطوير |
| `FX_DEVIATION_THRESHOLD_PCT` | نسبة انحراف `fx_rate_used` عن السعر المرجعي (`fxReferenceRate`) التي تُفعِّل `fx_rate_deviation_flag` وتوقِف اختيار العرض حتى اعتماد إضافي من `ADMIN_OWNER` — افتراضياً `0.05` (٥٪) |
| `PRODUCTION_SLA_MS` | مهلة `CUSTOMER_SLA`/`SUPPLIER_SLA` عند كل نقطة اعتماد إنتاج — افتراضياً 5 أيام (`432000000`)؛ تُقصَّر بيئياً للاختبار/التطوير |
| `ESCALATION_TIMEOUT_MS` | مهلة الرد بعد دخول `ESCALATION_REMINDER` قبل التصعيد التلقائي لـ`ESCALATION_ESCALATED` — افتراضياً 3 أيام (`259200000`) |
| `PORT` | منفذ الخادم |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_SECURE` / `SMTP_USER` / `SMTP_PASSWORD` / `SMTP_FROM_ADDRESS` | اعتمادات SMTP لإشعارات البريد — **اختيارية**: بلا قيم، الخادم يعمل بشكل طبيعي ويُسجِّل كل إشعار بحالة `SKIPPED_NO_CONFIG` بدل الإرسال الفعلي |
| `WHATSAPP_ACCESS_TOKEN` / `WHATSAPP_PHONE_NUMBER_ID` / `WHATSAPP_API_BASE_URL` | اعتمادات Meta WhatsApp Cloud API لإشعارات واتساب — **اختيارية** بنفس منطق SMTP أعلاه |
| `SEED_ADMIN_EMAIL` / `SEED_ADMIN_NAME` / `SEED_ADMIN_PASSWORD` | تُستخدَم مرة واحدة فقط بواسطة `pnpm --filter @apex/api seed:admin` لإنشاء أول حساب `ADMIN_OWNER` (idempotent — لا أثر لتكرار التشغيل إن وُجد إدمن أصلاً) |
| `FRONTEND_ORIGIN` | أصل الواجهة الأمامية المسموح له بطلبات CORS معتمدة (credentials) — افتراضياً `http://localhost:3001` للتطوير المحلي |
| `UPLOADS_DIR` | مجلد تخزين الملفات المرفوعة محلياً على القرص (`POST /uploads`) — افتراضياً `./uploads` |

## نطاق v1 الحالي

مسار عمودي كامل مُختبَر فعلياً من طرف لطرف: تقديم الطلب → المزايدة المغلقة (مؤقّت pg-boss فعلي، عزل RLS حقيقي بين الموردين) → التعاقد → **التحقق المزدوج للدفعة الأولى بـfour-eyes حقيقي** (مقترِح ومُعتمِد شخصان مختلفان فعلياً، لا مجرد فحص دور) → كشف الهوية → **مسار النزاع الإلزامي** (أي إلغاء بعد تأكيد دفعة أمانة يُحال تلقائياً لتسوية four-eyes بدل إلغاء صامت).

## نطاق v2 — "المسار السعيد" حتى COMPLETED

استكمال المسار العمودي بعد `IDENTITY_REVEALED` (حيث كان v1 يتوقف) وحتى `COMPLETED` فعلياً وحياً عبر HTTP:

- **`production/`**: رفع/اعتماد/رفض/إعادة رفع التصميم (Checkpoint 1) والفحص النهائي (Checkpoint 2)، بسجل `production_update` فعلي لكل رفع.
- **`escalation/`**: رد العميل/المورد على التصعيد يعيد الطلب بدقة لنقطة التجمّد (`resume_target_state`)، وقرار إداري نهائي (`ADMIN_OWNER`) عند غياب الاستجابة.
- **`shipping/`**: مستندات الشحن → تأكيد الدفعات المتبقية → الوصول للميناء.
- **`customs-fees/`**: **four-eyes حقيقي على رسوم التخليص** يطابق قيد DB الفعلي (`customs_fee_four_eyes`: `approved_by <> created_by`) — مشغّل يُنشئ، محاسب/مالك يعتمد قبل عرضها للعميل، ثم دفع + رفع إثبات + تحقق إداري.
- **`ratings/`**: توقيع العميل النهائي → تقييم المورد → إغلاق الطلب فعلياً على `COMPLETED`.

ثغرتان حقيقيتان في طبقة الدومين نفسها انكشفتا أثناء بناء v2 (لا فقط نقص apps/api) وأُصلحتا: `ESCALATION_TIMEOUT` لم يكن يُجدوَل إطلاقاً (الطلب يعلَق للأبد في `ESCALATION_REMINDER`)، و`SUPPLIER_SLA` كانت مُشار إليها (`cancelsTimers`) دون أي `schedulesTimer` يُجدوِلها فعلياً — كلاهما مُصلَح ومُختبَر حياً بمؤقّتات pg-boss فعلية (`ESCALATION_TIMEOUT_MS`/`PRODUCTION_SLA_MS` قابلتان للتقصير بيئياً).

## نطاق v2 — مسار التجديد (`RENEWAL_*`)

- **`renewals/`**: طلب تجديد بعد إلغاء اتفاقية (`AGREEMENT_CANCELLED_PENDING_RENEWAL`) → موافقة/رفض المورد → اعتماد/رفض الإدارة (`ADMIN_OWNER`) → استئناف الطلب **عند نقطة التجمّد الأصلية بدقة** (لا إعادة من الصفر)، أو مسار بديل أخف (اختيار مورد آخر) بدل إلغاء كامل عند رفض المورد.

**ثغرة ثالثة من نفس النمط** اكتُشفت وأُصلحت: الانتقال من حالة تصعيد إلى `AGREEMENT_CANCELLED_PENDING_RENEWAL` كان يُصفِّر `resume_target_state` **قبل** أن يستخدمه اعتماد الإدارة لاحقاً في سلسلة التجديد (لأن هذه الحالات لم تكن مصنَّفة ضمن أنواع "التعليق" في محرك الانتقالات) — فيُعاد الطلب دائماً لبداية التصنيع بدل نقطة توقّفه الحقيقية. أُضيف نوع تعليق ثالث (`RENEWAL`) لعمود `hold_type` (enum حقيقي في Postgres) وعُمِّمت كتلة "hold-state bookkeeping" لتشمله — مُختبَر حياً: طلب يتجمّد عند `PROD_CHECKPOINT_2` يستأنف فعلياً هناك بعد دورة تجديد كاملة، لا عند البداية.

مؤجَّل عمداً لمرحلة لاحقة: مسار المورد الخارجي الكامل (تحقق العملية بخطوتين مشغّل ثم مالك).

## نطاق v2 — الإشعارات الفعلية (بريد + واتساب)

- **`notifications/`**: عند كل انتقال حالة حقيقي (ليس الحلقات الذاتية كتعدد عروض المزايدة) يُسجَّل صف `notification_log` واحد لكل (مستلم × قناة) **داخل نفس معاملة الانتقال الذرية** — العميل عبر البريد (`customer.email`)، والمورد المسجَّل (إن عُيِّن) عبر البريد والواتساب (`registered_supplier.contact_email`/`whatsapp_phone`، حقلان جديدان — لم يكن للموردين أي بيانات تواصل من قبل). المحتوى ثابت وعام تماماً لكل الأحداث ("تحديث جديد على طلبك رقم #X، تفضل بالدخول") تطبيقاً لسياسة عدم كشف تفاصيل حساسة عبر الإشعار نفسه.
- الإرسال الفعلي عبر الشبكة (SMTP حقيقي عبر `nodemailer`، وMeta WhatsApp Cloud API عبر `fetch` المدمج) **best-effort غير متزامن** بعد التزام المعاملة، بواسطة عامل `pg-boss` مستقل (`send-notification`) — بنفس فلسفة مؤقّتات `scheduled_timer` القائمة: السجل في القاعدة هو مصدر الحقيقة، وفشل الشبكة لا يُرجِع الانتقال نفسه.
- الاعتمادات (`SMTP_*`/`WHATSAPP_*`) **اختيارية عمداً** خلافاً لبقية الأسرار — لا اعتمادات حقيقية متاحة في بيئة التطوير الحالية؛ التكامل حقيقي وفعلي بالكامل (لا محاكاة)، وبمجرد إضافة القيم الحقيقية في `.env` يعمل الإرسال الفعلي بلا أي تعديل كود. بغيابها، كل إشعار يُسجَّل بحالة `SKIPPED_NO_CONFIG` (أو `SKIPPED_NO_CONTACT` إن كان المستلم بلا بيانات تواصل أصلاً) بدل التعطّل.
- نطاق المستلمين مقصور على العميل والمورد المسجَّل — الإدارة تراقب عبر لوحة التحكم/سجل التدقيق مباشرة فلا حاجة لإغراقها بإشعارات على كل انتقال.

## الدخول الحقيقي + فجوات الباك-إند اللازمة للواجهة الأمامية

قبل بناء أي واجهة ويب، انكشف أن لا نظام دخول حقيقي كان موجوداً إطلاقاً (فقط `POST /auth/dev/{customer,supplier,admin}-token` — يُصدر JWT لأي id بلا أي تحقق، معطَّل تلقائياً خارج التطوير) ولا أي endpoint لإنشاء حساب عميل/مورد/إدمن أصلاً.

- **`POST /auth/customer/register`** (عام) — تسجيل ذاتي للعميل بكلمة مرور (bcrypt، 12 rounds) ودخول تلقائي فوري.
- **`POST /auth/{customer,supplier,admin}/login`** (عام) — دخول حقيقي بالبريد/كلمة المرور، 401 عام موحَّد لا يُفصح إن كان البريد موجوداً أم كلمة المرور خاطئة.
- **`POST /auth/{customer,supplier,admin}/change-password`** (بحراسة الدور المطابق) — تغيير كلمة المرور بعد التحقق من الحالية.
- **لا تسجيل ذاتي للمورد/الإدارة** (أمنياً) — `POST /admin/admins` (`ADMIN_OWNER` فقط، عبر قاعدة `ADMIN_ACCOUNT_MANAGE` في مصفوفة الصلاحيات) و`POST /admin/suppliers` (`ADMIN_OWNER`/`ADMIN_OPERATOR`، عبر `SUPPLIER_ACCOUNT_MANAGE`) لتزويد الحسابات لاحقاً. أول حساب `ADMIN_OWNER` يُنشأ عبر سكربت مستقل: `pnpm --filter @apex/api seed:admin` (يقرأ `SEED_ADMIN_*`، idempotent).
- نقاط `/auth/dev/*` **لم تُحذف** — لا تزال تخدم مجموعة اختبارات التكامل الحالية، ومحصورة بيئياً كما كانت.

بالتوازي، ثلاث فجوات حقيقية أخرى كانت ستمنع بناء أي واجهة عميل فعلياً:

- **`GET /orders/me`** و**`GET /orders/:id/detail`** (`CustomerAuthGuard`) — لم يكن يوجد أي قراءة تصلح للعميل إطلاقاً (`OrdersController.get` إداري فقط). الثاني قراءة مجمَّعة واحدة (عقد + خطة دفعات + دفعات + إيصالات + تحديثات إنتاج + مستندات شحن + رسوم جمركية + نزاعات + تصعيدات + تجديدات + سجل الانتقالات) بدل 8-10 نداءات منفصلة، ومحمية بفحص ملكية صريح (`customer_id`) فوق RLS — رفض بـ404 لا 403 عند طلب عميل آخر (لا يُؤكَّد وجود الطلب أصلاً).
- **`GET /bidding/:orderId/offers/customer-view`** (`CustomerAuthGuard`) — عروض مجهَّلة فعلياً (تسمية موضعية "المورد ١/٢" بدل `legal_name`/`registered_supplier_id`)، متاحة فقط بعد `REG_SHOWN_TO_CUSTOMER`.
- **`POST /uploads` + `GET /uploads/:id`** (`AnyActorAuthGuard` — يقبل أي من الحراسات الثلاث عبر passport متعدد الاستراتيجيات) — لم يكن يوجد أي مسار رفع ملفات إطلاقاً رغم أن كل DTO (إيصال، إثبات جمركي) يتوقع `fileUrl` جاهزاً. تخزين محلي على القرص (`UPLOADS_DIR`، لا اعتمادات سحابية متاحة حالياً — نفس منطق SMTP/WhatsApp)، لكن بتحكم وصول حقيقي: الكتابة تتحقق من `order_visible_to_actor()` (دالة SQL نفسها التي تعتمد عليها RLS) قبل الحفظ، والقراءة محمية عبر RLS مباشرة على جدول `uploaded_file` — لا تخزين علني (static) لملفات حساسة كإيصالات الدفع.

## بوابة العميل — `apps/web-customer`

أول واجهة ويب فعلية للمنصة (Next.js App Router + TypeScript + Tailwind، عربي/RTL بالكامل) تغطي دورة حياة الطلب كاملة من جهة العميل: تسجيل/دخول حقيقي → إنشاء طلب وتقديمه → مقارنة العروض المجهَّلة واختيار مورد → توقيع العقد → إشعار التحويل ورفع الإيصال → اعتماد/رفض نقاط فحص التصنيع → دفع الرسوم الجمركية ورفع الإثبات → فتح/متابعة النزاع → التجديد → تأكيد الاستلام → تقييم المورد.

- **الجلسة**: JWT في كوكي **httpOnly** (`apex_customer_token`) تُعيَّن حصراً من داخل Server Actions من جهة الخادم — لا يصل التوكن لجافاسكربت المتصفح إطلاقاً (لا يوجد refresh token في الباك-إند حالياً، فحماية التوكن من XSS هي خط الدفاع الوحيد المتاح).
- **الصفحة المركزية** `orders/[orderId]` مرنة (تايم لاين + لوحة "ماذا الآن؟" مبنية على جدول بحث `(current_state, hold_type)` في `lib/state-labels.ts`) بدل معالج (wizard) صلب — لأن النزاع/التصعيد/التجديد تراكب عرضي على الحالة (`hold_type`) لا استبدال لها.
- **رفع الملفات** (إيصالات، إثبات جمركي) عبر Server Actions تستدعي `POST /uploads` مباشرة بـ`FormData` (بلا وسيط proxy إضافي — Server Actions في Next.js تدعم ملفات حقيقية في `FormData` أصلاً).
- شغّل محلياً: `pnpm --filter @apex/web-customer dev -p 3001` (يحتاج `apps/api` يعمل على المنفذ 3000 مع `FRONTEND_ORIGIN=http://localhost:3001` في `.env` الجذر). تفاصيل أوسع في `apps/web-customer/README.md`.
- **مؤجَّل عمداً**: تخزين S3/سحابي للملفات (بديل التخزين المحلي الحالي على القرص).

## فجوات الباك-إند اللازمة لبوابة المورد

عند التحضير لبوابة المورد انكشفت 3 فجوات من نفس نمط ما وُجد لبوابة العميل:

- **`GET /bidding/board`** (`SupplierAuthGuard`) — `VIEW bidding_board` كان موجوداً فعلاً منذ هجرة RLS الأولى (مقصود تحديداً لهذا الغرض) لكن **لا كود استعلم منه إطلاقاً** — لم يكن هناك أي طريقة للمورد ليكتشف رقم طلب مفتوح للمزايدة رغم أن `POST /bidding/:orderId/offers` يعمل فعلياً.
- **`GET /orders/assigned-to-me`** (`SupplierAuthGuard`) — نظير `GET /orders/me` لكن بفلترة `registered_supplier_id` بدل `customer_id`.
- **`GET /orders/:id/detail-for-supplier`** (`SupplierAuthGuard`) — قراءة مجمَّعة كنظيرتها للعميل، لكن **لا تنضم لجدول `customer` إطلاقاً** (`customer.phone`: *"never shown to any supplier"* بتصميم `docs/schema.sql`، والجدول بلا RLS — عدم الاستعلام هو الضمان لا منطق تصفية إضافي) وتستبعد `shippingDocuments`/`customsFees`/`receipts` (سياسات RLS الحالية مقصورة على العميل بتصميم موثَّق صراحة).

## بوابة المورد — `apps/web-supplier`

ثاني واجهة ويب فعلية، بنفس هيكل `apps/web-customer` حرفياً (Next.js App Router + TypeScript + Tailwind، عربي/RTL بالكامل)، تغطي دورة حياة الطلب من جهة المورد: دخول حقيقي (**بلا تسجيل ذاتي** — حسابات الموردين تُنشأ عبر `POST /admin/suppliers` فقط) → اكتشاف الطلبات المفتوحة على لوحة المزايدة وتقديم عرض → رفع تصميم/فحص نهائي (QC) لنقاط الفحص الإنتاجية وإعادة الرفع عند الرفض → تأكيد استلام الدفعة → الرد على تصعيد موجَّه له تحديداً → فتح/متابعة نزاع → الموافقة على/رفض تجديد الاتفاقية.

- **الجلسة**: نفس نمط بوابة العميل تماماً — JWT في كوكي httpOnly (`apex_supplier_token`) يُعيَّن حصراً من داخل Server Actions.
- **لوحة التحكم** (`dashboard`) بقسمين: "عروض مفتوحة للمزايدة" (`GET /bidding/board`) و"طلباتي" (`GET /orders/assigned-to-me`) — الطلب ينتقل تلقائياً من الأول للثاني بعد فوز المورد بالمزايدة.
- **صفحة `orders/[orderId]`** المرنة نفسها (تايم لاين + "ماذا الآن؟") لكن بجدول action-map مختلف خاص بالمورد (`getSupplierAction` في `lib/state-labels.ts`) — يأخذ بالحسبان أن التصعيد الموجَّه للمورد (`escalation.actor === 'SUPPLIER_DELIVERABLE'`) فقط هو ما يستدعي رداً منه.
- **إعادة استخدام منطق الباك-إند القائم**: زر "إعادة الرفع" الواحد في صفحة الإنتاج يغطي كلا حالتي الرفض (`PROD_CHECKPOINT_1_REJECTED`/`PROD_CHECKPOINT_2_REJECTED`) لأن `ProductionService.resubmit()` نفسه يختار الحدث الصحيح تلقائياً بحسب `current_state` — لا حاجة لعملين منفصلين في الواجهة.
- شغّل محلياً: `pnpm --filter @apex/web-supplier dev -p 3002` (يحتاج `apps/api` يعمل على المنفذ 3000). تفاصيل أوسع في `apps/web-supplier/README.md`.
- **تحقق حي** (Playwright): إنشاء مورد عبر `POST /admin/suppliers` → دخول فعلي بكلمة المرور عبر `/login` → ظهور طلب منشور فعلياً على لوحة المزايدة → تقديم عرض فعلي من الواجهة → (عبر API مباشرة كإدارة/عميل) مراجعة العرض واعتماده ثم اختياره → تأكيد أن الطلب انتقل فعلياً لقائمة "طلباتي" وأن صفحة تفاصيله تعرض السجل الزمني الكامل بشكل RTL صحيح.
- **مؤجَّل عمداً**: قائمة ثالثة لعروض المورد المعلَّقة أثناء نافذة المراجعة القصيرة (`REG_ADMIN_REVIEW_BIDS`) — مقبولة كقيد v1 لأن نظام الإشعارات الفعلي يُعلم المورد بأي تحوّل.

## بوابة الإدارة — `apps/web-admin`

ثالث وآخر واجهة ويب، وأشمل الثلاث نطاقاً: تغطي كل إجراءات الإدارة عبر دورة حياة الطلب بأكملها — لا مجموعة فرعية مختارة، بل مطابقة كاملة لأفعال الإدارة المتاحة في `packages/domain` (مراجعة، فحص مورد خارجي، مزايدة/سعر صرف، عقد/دفعات، لوجستيات/جمارك، نزاعات، تصعيدات، تجديدات، حسابات).

- **`state-labels.ts` أكبر جدول action-map في المشروع** (`getAdminAction(orderId, state, holdType)`) — مقسَّم لدوال فرعية حسب عائلة الحالة بدل `switch` ضخم واحد، لأن الإدارة تتدخل في كل مرحلة تقريباً خلافاً للعميل/المورد.
- **لوحة التحكم**: قسمان — "طلبات جديدة" (`GET /orders?state=SUBMITTED`، بانتظار تأكيد العربون) و"طلبات تحتاج إجراءً إدارياً" (`GET /orders/queue/needs-admin-action`) مُصنَّفة حسب الفئة، بالإضافة لبحث عام عبر `GET /orders` بالفلاتر.
- **صفحة مركز الطلب** (`orders/[orderId]`) هي الأشمل بين البوابات الثلاث: تعرض PII العميل كاملاً (مقصود هنا، خلافاً لتقييده عمداً في نسختي العميل/المورد)، بيانات المورد (مسجَّل أو خارجي)، خطة الدفع والدفعات والإيصالات، رسوم التخليص، النزاعات/التصعيدات/التجديدات، السجل الزمني، **وسجل التدقيق الفعلي** (أول عرض فعلي لصفوف `audit_log`، لا فقط تحقق سلامة السلسلة).
- **نمطا four-eyes مبنيان صراحة كمسارين منفصلين في الواجهة** (لا تعميم زائف): "رشّح ثم اعتمد" (تحقق الدفعات، فحص المورد الخارجي، الاسترداد الإلزامي — قائمة اختيار معتمِد مؤهَّل تستبعد المُرشِّح نفسه ومن يشارك دوره عند الاسترداد الإلزامي) مقابل "اعتماد مباشر" (رسوم التخليص — أي أدمن آخر مؤهَّل غير منشئ الرسم، بلا خطوة ترشيح مسبقة، لأن `customs-fees.service.ts` في الباك-إند نفَّذها بهذا الأسلوب المختلف عمداً منذ البداية).
- **شاشة الحسابات** (`accounts`): سرد + إنشاء + تعطيل/تفعيل لحسابات الإدارة والموردين معاً — الأزرار تُخفى محلياً حسب دور المستخدم الحالي (تجميلي فقط؛ التنفيذ الفعلي محمي في الباك-إند دوماً)، وزر تعطيل الحساب الخاص بالمستخدم الحالي نفسه مخفي دوماً.
- **الجلسة**: نفس نمط البوابتين الأخريين — JWT في كوكي httpOnly (`apex_admin_token`) يُعيَّن حصراً من داخل Server Actions. **لا صفحة تسجيل ذاتي** — أول حساب `ADMIN_OWNER` عبر `pnpm --filter @apex/api seed:admin`.
- شغّل محلياً: `pnpm --filter @apex/web-admin dev -p 3003` (يحتاج `apps/api` يعمل على المنفذ 3000). تفاصيل أوسع في `apps/web-admin/README.md`.
- **تحقق حي** (Playwright): دخول `OWNER` حقيقي → تأكيد عربون من لوحة التحكم → صفحة تفاصيل تعرض PII العميل والسجل الزمني بشكل RTL صحيح → إنشاء حسابي `OWNER` ثانٍ ومورد جديد من شاشة الحسابات → مسار فحص مورد خارجي كامل بشخصين إداريين حقيقيين منفصلين فعلياً (المُرشِّح لا يستطيع اعتماد ترشيحه هو، والمُعتمِد الثاني يسجّل دخوله بجلسة منفصلة تماماً ليعتمد فعلياً) → دورة نسيت/إعادة تعيين كلمة المرور كاملة عبر الواجهة تنتهي بنجاح الدخول بكلمة مرور جديدة.
- **مؤجَّل عمداً**: لا شيء جوهري من نطاق الإدارة نفسه — الفجوات المتبقية عامة على المنصة كلها (مسار المورد الخارجي كان الوحيد الناقص فعلياً، وهو مبني الآن بالكامل ضمن هذه المرحلة).

## فجوات باك-إند حرجة اكتُشفت وسُدَّت عند التحضير لبوابة الإدارة

عند التخطيط لبوابة إدارة شاملة، انكشف أن مسارين كاملين من آلة الحالة كانا بلا أي تنفيذ في `apps/api` منذ البداية — ليسا تفاصيل ناقصة، بل طلبات تعلق للأبد بمجرد الوصول إليها:

- **مسار المورد الخارجي (`EXT_VETTING_*`) كان بلا أي controller/service** رغم وجود جدول `external_supplier` وحدثي `approve_vetting`/`reject_vetting` في جدول الانتقالات منذ الهجرة الأولى — أي طلب يختار "مورد خارجي" كان يعلق فعلياً في `EXT_VETTING_DOCS` للأبد. وحدة جديدة `apps/api/src/external-suppliers/`: `POST /orders/:orderId/external-supplier` (تسجيل بيانات المورد المرشَّح)، ثم اعتماد نهائي **four-eyes حقيقي** (`vetting/propose-approval` + `vetting/approve`، عبر `FinancialApprovalService` بنفس نمط الدفعات/النزاعات، `entityType:'order'`) — `OWNER` فقط، ولا بد من شخصين مختلفين. الرفض (`vetting/reject`) يسلسل تلقائياً `reject_vetting → auto_close` في نداء واحد فينزل مباشرة على `CANCELLED`، بنفس نمط `orders.service.ts`'s `reject()`.
- **حدثا `extend_deadline`/`cancel_order` من `REG_BIDS_EXPIRED_NO_OFFERS`/`REG_NO_OFFER_SELECTED` كانا بلا أي endpoint** رغم وجودهما في الجدول — طلب تنتهي مزايدته بلا عروض، أو يرفض العميل كل العروض، كان يعلق للأبد أيضاً. أُضيف `POST /bidding/:orderId/extend-deadline` و`POST /bidding/:orderId/cancel` (الحدث الواحد يغطي كلا الحالتين المصدر، لأن المحرك يبحث بـ`(from, event)`).

## بوابة الإدارة — فجوات القراءة/الحسابات/كلمة المرور اللازمة لها

قبل أي واجهة إدارة، تحقُّق مباشر من الكود كشف أن الإدارة **لم يكن لديها أصلاً أي وسيلة لتصفح الطلبات** — فقط `GET /orders/:id` (فردي، يتطلب معرفة الـUUID مسبقاً)، ولا أي سرد لحسابات الإدارة/الموردين، ولا أي آلية "نسيت كلمة المرور". هذه الثلاث فجوات سُدَّت جميعها:

- **`GET /orders`** (فلاتر: `state`, `holdType`, `customerId`, `supplierId`, `page`, `pageSize` — حد أقصى 100 لكل صفحة) و**`GET /orders/queue/needs-admin-action`** (قائمة "تحتاج إجراء إدارياً الآن" مُصنَّفة بفئة). الفئة **مُشتقَّة من جدول الانتقالات نفسه لا مكتوبة يدوياً**: دالة جديدة `packages/domain/src/states/admin-queue.helper.ts` تمسح `TRANSITIONS` وتحسب أي حالة لها انتقال صادر بأدوار إدارية حصراً (`ADMIN_ACTIONABLE_STATES`) — إن تغيَّر جدول الانتقالات مستقبلاً، هذه القائمة تتغيّر تلقائياً معه، مع اختبار وحدة يُثبِّت المجموعة الحالية (38 حالة). قائمة العرض الفعلية في `GET /orders/queue/needs-admin-action` أضيق عمداً (`ADMIN_QUEUE_CATEGORY` في `apps/api`، 24 حالة عبر 9 فئات) لأن معظم حالات `PROD_*`/`CONTRACT_*` "قابلة للإجراء الإداري" فقط لأن الأدمن يملك دوماً خيار الإلغاء الاستثنائي — عرضها كلها في لوحة "تحتاج إجراء الآن" كان سيُغرقها بضجيج، فحُصرت القائمة بالحالات التي القرار الإداري فيها هو الخطوة التالية المتوقَّعة فعلاً (اختبار يؤكّد أن كل فئة معروضة عضو حقيقي في `ADMIN_ACTIONABLE_STATES`، فلا تنجرف القائمتان عن بعضهما).
- **`GET /orders/:id/detail-for-admin`**: أشمل قراءة مجمَّعة (تشمل PII العميل كاملاً — مقصود هنا خلافاً لنسختي العميل/المورد المقيَّدتين عمداً)، بالإضافة إلى المورد (مسجَّل أو خارجي)، والعروض، وصف واحد جديد لحالة اعتماد four-eyes الحالية (`financialApprovals`) — استعلام واحد بسيط بما أن `FinancialApprovalService` تُخزِّن دوماً `entity_type:'order'` (وليس كما افتُرض أولياً معرّف كل سجل فرعي)، فلا حاجة لتجميع معرّفات دفعات/نزاعات فرعية أولاً.
- **`GET /orders/:id/audit-log`**: أول قراءة فعلية لسجل التدقيق (سابقاً فقط `GET /audit/verify-chain` كتحقق منطقي/منطقي من سلامة السلسلة، بلا عرض للصفوف نفسها).
- **`GET /admin/admins`/`GET /admin/suppliers`** (سرد، بلا `password_hash` أبداً) — سدّ فجوة حقيقية في تجربة four-eyes القائمة أصلاً: مقترح دفعة/نزاع يحتاج تمرير `approverId` UUID، ولم تكن هناك أي وسيلة لمعرفة أي admin id يقابل أي اسم/دور. **`GET /auth/admin/me`**: الـJWT الإداري لا يحمل اسماً (فقط دور+id)، فترويسة البوابة وتصفية "استبعد نفسي" في قائمة اختيار المعتمِد تحتاجان قراءة فعلية.
- **تفعيل/تعطيل الحسابات** (`POST /admin/{admins,suppliers}/:id/{deactivate,reactivate}`) بحارس قفل ذاتي حقيقي: لا يمكن لأدمن تعطيل حسابه هو (بلا فائدة، مخاطرة فقط)، ولا يمكن تعطيل **آخر `OWNER` نشط** إطلاقاً (فقدانه يعني فقدان القدرة على إدارة الحسابات كلياً، بما أن `ADMIN_ACCOUNT_MANAGE` حصراً لـ`OWNER`). اكتُشف أثناء البناء أن `loginSupplier` لم يكن يتحقق من `is_active` إطلاقاً (خلافاً لـ`loginAdmin`) — أُصلح ليطابق نفس السلوك، وإلا كان تعطيل مورد لا يمنع تسجيل دخوله فعلياً.
- **نسيت/إعادة تعيين كلمة المرور** لكل الأدوار الثلاثة: هجرة جديدة (`password_reset_token`، هاش sha256 للتوكن لا bcrypt — يحتاج بحثاً بالقيمة الحرفية)، `POST /auth/{customer,supplier,admin}/forgot-password` (رد ثابت دائماً بصرف النظر عن وجود البريد، لمنع اكتشاف الحسابات)، `POST /auth/{customer,supplier,admin}/reset-password` (صلاحية 30 دقيقة، استخدام واحد). الإرسال عبر `EmailProvider.send()` مباشرة (وليس `NotificationsService` المرتبط حصراً بانتقالات الطلبات) — رابط إعادة التعيين يُبنى حسب أصل البوابة الصحيحة (`FRONTEND_ORIGIN_{CUSTOMER,SUPPLIER,ADMIN}`، ثلاثة حقول جديدة منفصلة عن `frontendOrigin` الأصلي المخصَّص لـCORS فقط).
- **مُصلَح لاحقاً**: `AdminJwtStrategy`/`SupplierJwtStrategy` كانتا تتحققان من توقيع الـJWT فقط، بلا استعلام `is_active` لكل طلب — تعطيل حساب كان يمنع تسجيل الدخول *التالي* فقط، دون إبطال توكن ساري صدر مسبقاً (حتى 12 ساعة). أُصلح بحقن `KYSELY` مباشرة في كلتا الاستراتيجيتين واستعلام `is_active` حياً في `validate()` (لا حاجة لجدول إبطال منفصل — `admin_user`/`registered_supplier` بلا RLS فيمكن استعلامهما مباشرة بلا `SET LOCAL app.actor_type`)؛ تعطيل حساب يُبطل الآن توكنه الساري فوراً على الطلب التالي مباشرة، مُختبَر حياً (`admin-portal.integration-spec.ts`).

## سجل الإصلاحات المكتشفة أثناء البناء

عدة ثغرات تصميمية حقيقية (لا تفاصيل تجميلية) انكشفت فقط أثناء التشغيل الفعلي ضد PostgreSQL حي — لا أثناء المراجعة أو التخطيط — وأُصلحت فوراً، بينها: قيد "منع نزاعين متزامنين" كان بلا أثر فعلياً وتم نقله لمكانه الصحيح، `state_version` كان يتعارض مع الحلقات الذاتية (كتعدد عروض المزايدة) فيُفسد مؤقّت الموعد النهائي، RLS الموحَّد بين القراءة والكتابة كان يمنع كتابات مشروعة بالفعل تحقق منها محرك الانتقالات، واعتماد دائري بين خدمتين تسبَّب بتوقف صامت للخادم بلا أي خطأ ظاهر. كل إصلاح موثَّق في تعليق أعلى الكود/الهجرة المعنية مباشرة — ابحث عن كلمة "discovered" أو "إصلاح" في `migrations/` و`src/` لسياق كل قرار.

## سجل مراجعة أمنية/منطقية إضافية (بعد الإطلاق الأول)

مراجعة متعددة الزوايا للكود القائم (منطق، سلوك محذوف، تتبع بين الملفات، إعادة استخدام، كفاءة، عمق الحل) مع تحقق مستقل لكل ملاحظة، كشفت 10 ثغرات حقيقية أُصلحت جميعها ووُثِّقت باختبارات تكامل جديدة (`full-flow.integration-spec.ts`، 5 اختبارات إضافية):

- **four-eyes الحقيقي على تأكيد الدفعة**: لم يكن يُفرَض أن المُعتمِد النهائي بدرجة OWNER/ACCOUNTANT — أُصلح مركزياً في `FinancialApprovalService` (يقرأ `finalApproverRoles`/`approverRoleMustDifferFromSubmitter` من `PERMISSION_MATRIX` بدل فحوصات مكرَّرة يدوياً في كل وحدة).
- **تعليق مضلِّل** يشير لـ`FourEyesGuard` غير موجود إطلاقاً في الكود — أُزيل واستُبدل بتوثيق دقيق لمكان التطبيق الفعلي.
- **تحقق ملكية الطلب مفقود** عند التحقق من الإيصالات (`markReceiptVerified`/`rejectReceipt`) — كان يمكن لمعرّف دفعة من طلب آخر أن يُغيّر حالة الطلب الحالي.
- **`DbTransactionInterceptor` كان يفشل بأمان زائف** (fail-open لدور SYSTEM كامل الصلاحيات) عند غياب هوية الفاعل — أصبح يرفض الطلب افتراضياً (`fail-closed`) إلا للمسارات المُعلَّمة صراحةً بـ`@Public()`.
- **`catch` فارغ يبتلع كل الأخطاء** بعد تأكيد الدفعة، بما فيها أخطاء تزامن حقيقية — أُصلح ليمرر فقط رفض الانتقال المتوقَّع.
- **سجل نزاع لا يُنشأ** عند الانتقال من حالة تصعيد مباشرة لحالة نزاع — أُصلح شرط الإنشاء.
- **`fx_rate_deviation_flag`** كان موثَّقاً في 3 مواضع وغير منفَّذ إطلاقاً — أصبح يُحسب فعلياً مقابل سعر مرجعي مستقل، ويحظر اختيار العرض حتى اعتماد `ADMIN_OWNER` إضافي (`POST /bidding/:orderId/fx-deviation/approve`).
